# Настройки: редактирование имени и аватара пользователя — план реализации

> Статус: план на согласование, код ещё не менялся.

## 1. Как это работает сейчас (по коду)

В проекте фактически **две параллельные "пользовательские" системы**, и это ключевая находка:

1. **Room-таблица `users`** (`UserEntity` / `UserDao`, поля `id, name, passwordHash, avatarUri, createdAt`) —
   существует в схеме БД, DAO зарегистрирован в Hilt (`AppModule.provideUserDao`), но **нигде не используется**:
   `insertUser` / `getUser` / `updateName` / `updatePassword` не вызываются ни из одного репозитория,
   ViewModel или сервиса. Это мёртвый код.
2. **DataStore Preferences** (`data/repository/UserRepository.kt`, файл `settings`) — это то, что реально
   работает сейчас: хранит `username`, `passwordHash`, `avatarUri`, `onboardingCompleted` как отдельные ключи.

Экран настроек (`ui/settings/SettingsScreen.kt` + `SettingsViewModel.kt`) сегодня:
- **Аватар**: уже частично работает — по клику на аватар открывается системный пикер (`GetContent`),
  выбранный `content://` URI сохраняется как есть (без ресайза) в DataStore (`UserRepository.avatarUri`).
  Есть попытка `takePersistableUriPermission`, но `ActivityResultContracts.GetContent` не гарантирует, что
  источник вернёт URI, на который выдаётся persistable-разрешение (зависит от галереи/файлового менеджера) —
  на части устройств/поставщиков контента это падает с `SecurityException`, на части — URI протухает после
  перезапуска приложения, и аватар "слетает". Отсюда и ощущение "аватар нельзя изменить".
- **Имя**: значение `username` загружается в `SettingsState`, но **в самом экране нет ни `TextField`, ни
  кнопки сохранения** — имя нигде не отображается и не редактируется. Отсюда "имя нельзя изменить".
- Дефолтный пользователь сегодня создаётся в `OnboardingViewModel.initApp()` через
  `UserRepository.initDefaultUser()`, но это про DataStore, не про Room-таблицу `users`, и там же обнаружен
  смежный баг: `initDefaultUser()` пишет `setUsername("12345")` — то есть имени присваивается значение
  дефолтного пароля (видимо, копипаста). Так как имя нигде не отображается, баг незаметен.

Приватные настройки (`PrivateSettingsViewModel`) используют `UserRepository.passwordHash` (DataStore) для
гейта — это отдельный, не связанный с `users.passwordHash` механизм.

## 2. Целевое поведение (по ТЗ)

- Единственный источник правды для имени и аватара — **Room-таблица `users`** (`users.name`, `users.avatarUri`).
- В БД всегда ровно одна запись пользователя.
  - Если записи нет — создаётся при инициализации приложения со значениями по умолчанию:
    `name = "username"`, `passwordHash = ""`.
- Экран "Настройки":
  - **Аватар**: клик → пикер изображения → ресайз до небольшого размера → сразу сохраняется в
    `users.avatarUri` (без дополнительного подтверждения).
  - **Имя**: редактируемое поле + отдельная кнопка **"Сохранить имя"** (сохранение не автоматическое).
- Остальной функционал экрана "Настройки" (приватные настройки, debug, версия приложения) — не трогаем.

## 3. Архитектурное решение

- `UserRepository` (`data/repository/UserRepository.kt`) остаётся, но получает вторую зону ответственности:
  - существующие DataStore-методы (`passwordHash`, `onboardingCompleted`, `initDefaultUser` и т.д.) —
    **не трогаем**, они обслуживают гейт приватных настроек и онбординг, это вне рамок задачи;
  - добавляются новые методы поверх инжектированного `UserDao`, работающие с Room-таблицей `users`:
    - `val user: Flow<UserEntity?>` — реактивное чтение единственной записи;
    - `suspend fun ensureDefaultUser()` — если `getUserSync() == null`, вставить
      `UserEntity(name = "username", passwordHash = "")`;
    - `suspend fun updateName(name: String)` — `UserDao.updateName(id, name)` по id текущего пользователя;
    - `suspend fun saveAvatar(uri: Uri): Result<Unit>` — ресайз + сохранение файла + `UserDao` update
      (см. п. 4).
  - Схема БД не меняется (все нужные поля в `UserEntity` уже есть) — новой Room-миграции не требуется.
- `ensureDefaultUser()` вызывается из `OnboardingViewModel.initApp()` рядом с существующим
  `userRepository.initDefaultUser()` — этот метод уже гарантированно выполняется при каждом холодном
  старте приложения (Onboarding — стартовый экран навигации), поэтому дополнительный `Application`/DB-callback
  не нужен.
- `SettingsViewModel`/`SettingsScreen` переключаются с DataStore-полей `username`/`avatarUri` на новые
  Room-based методы `UserRepository`. Старые DataStore-поля `username`/`avatarUri` (и их сеттеры) после
  этого становятся неиспользуемыми — предлагается удалить их из `UserRepository` в рамках этой же задачи
  (мёртвый дублирующий код, ключи `password_hash`/`onboarding_completed` в том же классе не трогаем).

## 4. Ресайз и хранение аватара

Текущая проблема — хранение "сырого" `content://` URI. Вместо этого:

1. По выбранному `Uri` декодировать `Bitmap` (с `inSampleSize` по размеру исходника, чтобы не грузить
   гигантскую картинку в память).
2. Обрезать по центру до квадрата и уменьшить до **256×256 px** (аватар в UI показывается 120dp кругом —
   256px с запасом на плотность экрана и достаточно "небольшой" по весу).
3. Сохранить как JPEG (quality ~85) в приватное хранилище приложения:
   `context.filesDir/avatars/avatar_<timestamp>.jpg`.
4. Удалить предыдущий файл аватара (если был) — чтобы не копились файлы и не было расхождения с БД.
5. В `users.avatarUri` записать `file://...` путь к новому файлу.

Плюсы: файл живёт во внутреннем хранилище приложения — не нужны `persistable URI permission`,
не отвалится после перезапуска/сброса разрешений; смена имени файла на каждый апдейт естественным образом
сбрасывает кэш Coil (не будет показывать старую картинку под тем же URI).

## 5. UI экрана "Настройки"

- Аватар: без изменений в части клика/пикера, меняется то, что происходит после выбора файла — вызывается
  `viewModel.saveAvatar(uri)`, который делает ресайз и сразу пишет в БД (без промежуточных подтверждений).
- Блок с именем (новый): `OutlinedTextField` с текущим именем (локальный черновик, инициализируется из
  `state.name`, не перетирается при каждой рекомпозиции) + кнопка **"Сохранить имя"** рядом/под полем.
  - Кнопка недоступна, если поле пустое (`isBlank()`) — имя не может быть пустой строкой.
  - По нажатию — `viewModel.saveName(draft.trim())`, короткая визуальная отметка об успехе (не блокирующая,
    без диалогов).

## 6. Пошаговый план реализации

1. `UserRepository.kt`: добавить `UserDao` в конструктор; добавить `user: Flow<UserEntity?>`,
   `ensureDefaultUser()`, `updateName()`, `saveAvatar()`; удалить неиспользуемые DataStore
   `username`/`avatarUri`/`setUsername`/`setAvatarUri`.
2. `OnboardingViewModel.kt`: вызвать `userRepository.ensureDefaultUser()` в `initApp()`.
3. Новый файл `core/util/AvatarImageUtil.kt` (или приватная функция в `UserRepository`) — логика
   декодирования/кропа/ресайза/сохранения файла аватара.
4. `SettingsViewModel.kt`: заменить чтение `username`/`avatarUri` из DataStore на `userRepository.user`;
   добавить `saveName(name: String)` и `saveAvatar(uri: Uri)`; добавить в `SettingsState` поле для
   черновика имени / индикатора "сохранено".
5. `SettingsScreen.kt`: добавить UI-блок редактирования имени (`OutlinedTextField` + кнопка "Сохранить
   имя"); переключить обработчик выбора аватара на `viewModel.saveAvatar(uri)`.
6. Ручная проверка: чистая установка (нет записи в `users`) → после онбординга в БД должна появиться ровно
   одна запись `name="username", passwordHash=""`; смена имени; смена аватара; перезапуск приложения —
   аватар и имя должны сохраняться.
7. Юнит-тест на `ensureDefaultUser()` (не создаёт вторую запись при повторном вызове) — по аналогии с
   существующими тестами в `app/src/test`.

## 7. Явные решения по умолчанию (можно поправить перед реализацией)

| Вопрос | Принятое решение |
|---|---|
| Целевой размер аватара | 256×256 px, JPEG q=85, квадратная обрезка по центру |
| Где хранить файл аватара | `filesDir/avatars/avatar_<timestamp>.jpg`, старый файл удаляется при замене |
| Пустое имя | Кнопка "Сохранить имя" неактивна, если поле пустое после `trim()` |
| DataStore-поля `username`/`avatarUri` | Удаляются как дубли (после переезда на Room), `passwordHash`/`onboarding` в `UserRepository` — не трогаем |
| Место вызова `ensureDefaultUser()` | `OnboardingViewModel.initApp()` (выполняется на каждом холодном старте) |
| Связь `users.passwordHash` с гейтом приватных настроек | Никакой — гейт продолжает работать через отдельный DataStore-пароль (вне рамок задачи), `users.passwordHash=""` остаётся неиспользуемым техническим полем |

## 8. Вне рамок этой задачи

- Логика кнопок "Приватные настройки" и "Debug" на экране настроек.
- Проверка/смена пароля приватных настроек (остаётся на DataStore, дефолт `"12345"` как в `INSTALL_GUIDE.md`).
- Объединение двух пользовательских систем (Room `users` vs DataStore) в одну — потенциальная задача на
  будущее, здесь только устраняется дублирование по полям `name`/`avatarUri`.
