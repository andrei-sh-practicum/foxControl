## 1. Критичные

### B-1. Глобальный лимит — нерабочая функция

> **Решение (2026-09-23): ✅ В работу.** Вариант **А** — довести до рабочего состояния. Правило включения (п. 4): `minutes > 0` ⇒ лимит включён, `0` ⇒ выключен; отдельного `Switch` нет.

**Где:** `PrivateSettingsViewModel.kt:108`, `PrivateSettingsScreen.kt:396-423`, `UsageStatsRepository.kt:239`, `GlobalLimitDao.kt`, `AlertManager.kt:28`

**Проблема.** Диалог «Общий дневной лимит» меняет только `state.globalDailyLimitMinutes` в памяти. `setGlobalLimit()` нигде не вызывается, а внутри делает `UPDATE global_limit … WHERE id = 1`, хотя строка с `id = 1` нигде не создаётся (`insertGlobalLimit()` не вызывается). У `GlobalLimitEntity.enabled` по умолчанию `false`, и включить его негде.

**Последствие.** `checkGlobalLimit()` всегда возвращает `false`, алерт «Весь смартфон» не показывается никогда. После перезахода на экран значение сбрасывается на 120.

**Варианты решения:**

- ⭐ **А. Довести функцию до рабочего состояния.**
  1. `GlobalLimitDao`: запись через `insertGlobalLimit(GlobalLimitEntity(id = 1, …))` (`REPLACE` = upsert) вместо `UPDATE`.
  2. Добавить в интерфейс `UsageStatsRepository` `getGlobalLimit(): GlobalLimitEntity?` и `setGlobalLimit(minutes, enabled)`.
  3. `PrivateSettingsViewModel`: в `init` загружать лимит из БД. В диалоге — локальный черновик и сохранение по «Готово» (сейчас каждое нажатие клавиши пишет в state, а `toIntOrNull() ?: 0` превращает пустое поле в `0`). «Отмена» не должна менять значение.
  4. Включение лимита: либо `Switch` в блоке «Общий дневной лимит», либо правило «`minutes > 0` ⇒ включён». Нужно решение владельца.
  5. Итог для глобального лимита должен считаться по **всем** сессиям, без фильтра «< 1 мин» (см. B-18).
- **Б. Убрать функцию.** Удалить блок и диалог из `PrivateSettingsScreen`, событие `OnGlobalLimitChanged`, поле состояния, ветку global в `AlertManager`, `checkGlobalLimit`. Таблицу `global_limit` и сущность **оставить**, чтобы не делать миграцию БД.

**Проверка:** поставить лимит 1 мин → через 1–2 мин использования появляется overlay и уведомление «Весь смартфон» (один раз за день) → значение сохраняется после перезапуска приложения.

### B-3. `MIGRATION_2_3` не соответствует схеме

> **Решение (2026-09-23): ⏸ Оставить как есть.** Вариант **В**. Все устройства уже на схеме v3+, `MIGRATION_2_3` не трогаем.

**Где:** `Migrations.kt:10-40`

**Проблема.** Миграция создаёт `email_recipient (id, email, enabled)`, `email_settings (id, smtp_host, …)`, `report_send_log (id, date, status, error, sent_at)`. Сущности же ожидают `email_recipients (id, email, name, isActive, createdAt)`, `email_settings (key PK, value, updatedAt)`, `report_send_log (id, date, status, errorMessage, recipientCount, sentAt)`.

**Последствие.** При обновлении с БД v2 Room после миграции проверяет схему и бросает `IllegalStateException: Migration didn't properly handle …`. `fallbackToDestructiveMigration()` это **не** перехватывает, поэтому приложение падает на старте. Масштаб ограничен: по истории git версия БД 3 была уже в самом первом коммите (`8fd2eea`, `1.2.9`), значит, затронуты только установки **старше 1.2.9**.

**Варианты решения:**
- **А. Переписать миграцию.** Сначала выполнить этап 7.1 рефакторинга (экспорт схемы Room), взять `createSql` для этих трёх таблиц из `schemas/…/4.json` (между v3 и v4 они не менялись, `MIGRATION_3_4` только удаляет `service_downtime_events`) и заменить SQL в `MIGRATION_2_3`. Перед созданием выполнить `DROP TABLE IF EXISTS` для неверных имён (`email_recipient`). Добавить инструментальный тест `MigrationTestHelper` для переходов 2→3→4.
- ⭐ **Б. Удалить `MIGRATION_2_3`.** Для v2 тогда сработает `fallbackToDestructiveMigration()`: БД пересоздастся (данные старой версии пропадут), но падения не будет. Подходит, если установок старше 1.2.9 у пользователей нет или их данные не важны.
- **В. Оставить как есть**, если подтверждено, что все устройства уже на v3+. Зафиксировать это в `CLAUDE.md`.

### B-5. Трекинг не перезапускается после восстановления разрешений

> **Решение (2026-09-23): ✅ В работу.** Вариант **А** — разделить логику на «критичные» и «все» разрешения.

**Где:** `TrackingForegroundService.kt:75-129`

**Проблема.** Каждую минуту при `!allGranted`:
- если потеряно критичное разрешение (usage stats или overlay), вызывается `restartService()`: `trackingJob.stop()`, а через 5 с `start()` — **только если `allGranted`** (все 4, включая уведомления и батарею);
- если критичные вернулись, а некритичные нет, `restartService()` больше не вызывается, а ветка «Permissions RESTORED» срабатывает только при `allGranted` и лишь пишет в лог.

**Последствие.** Сценарий: пользователь отозвал usage access, потом вернул, но уведомления выключены. `TrackingJob` остановлен навсегда: нет сессий, heartbeat, алертов и email-отчётов. Лечится только перезапуском сервиса (перезагрузка или открытие приложения, где `MainActivity` запускает сервис, но `onCreate` сервиса уже не вызовется повторно).

**Варианты решения:**
- ⭐ **А. Разделить логику на «критичные» и «все» разрешения.**
  - Потеря критичного разрешения → `trackingJob.stop()` **один раз** на переходе (сейчас stop и перезапуск повторяются каждую минуту).
  - Критичные разрешения на месте, а джоб не запущен → `trackingJob.start()` (`start()` уже идемпотентен через `isRunning`, для надёжности сделать его `AtomicBoolean`, см. рефакторинг T-3).
  - Для перезапуска использовать `PermissionHelper.areCriticalPermissionsGranted()`, а не `allGranted`.
  - Некритичные разрешения только логировать.
- **Б. Не останавливать джоб при потере разрешений.** Без usage access `queryUsageStats` просто вернёт пустой список (это уже обрабатывается), без overlay сработает fallback-уведомление. Проще, но heartbeat тогда будет показывать «сервис жив» при фактически неработающем сборе.

**Проверка:** выключить уведомления → отозвать usage access → через 2 мин вернуть → в Debug/логе видно `TrackingJob STARTED`, сессии снова пишутся.

### B-6. Онбординг может зависнуть

> **Решение (2026-09-23): ✅ В работу.** Вариант **А** (все 4 подпункта).

**Где:** `OnboardingViewModel.kt:46, 73`, `PermissionHelper.kt:135`, `OnboardingScreen.kt:123-139`

**Проблема.** Переход на Home происходит только при `allGranted` = usage stats **и** overlay **и** уведомления **и** батарея. При этом:
- у карточки «Уведомления» нет кнопки (`onAction = null`), а runtime-запрос `POST_NOTIFICATIONS` (Android 13+) нигде не делается;
- батарея подписана как «(опционально)», но на деле блокирует вход;
- разрешения перепроверяются только по кнопке «Проверить ещё раз», а не при возврате из системных настроек.

**Последствие.** На Android 13+ после установки уведомления выключены по умолчанию, поэтому пользователь застревает на онбординге. Некоторые OEM не дают отключить оптимизацию батареи, и там тоже тупик.

**Варианты решения:**
- ⭐ **А.**
  1. Критерий завершения — критичные разрешения (usage stats + overlay). Уведомления и батарею показывать как рекомендуемые, с кнопкой «Продолжить без них».
  2. Карточка «Уведомления»: на API 33+ — `rememberLauncherForActivityResult(RequestPermission(POST_NOTIFICATIONS))`. Если запрос отклонён навсегда, открывать `Settings.ACTION_APP_NOTIFICATION_SETTINGS`.
  3. Перепроверять разрешения на `Lifecycle.Event.ON_RESUME` (`LifecycleEventEffect`), чтобы после возврата из настроек статус обновлялся сам.
  4. Согласовать с B-5: «критичные» определяются в одном месте (`PermissionHelper`).
- **Б. Минимально:** только добавить кнопку для уведомлений (п. 2) и считать батарею необязательной. Критерий «уведомления обязательны» остаётся.

**Проверка:** чистая установка на Android 13+, уведомления запрещены → онбординг проходится. На Android 8–12 поведение прежнее.

### B-7. `queryUsageStats` с `INTERVAL_YEARLY`

> **Решение (2026-09-23): ⏸ Отложено.** Игнорируем на данном этапе.

**Где:** `TrackingJob.kt:128-132`

**Проблема.** Вызывается `queryUsageStats(3, start, end)` с комментарием `// INTERVAL_DAY`, но `3` — это `INTERVAL_YEARLY` (`DAILY = 0`, `WEEKLY = 1`, `MONTHLY = 2`, `YEARLY = 3`, `BEST = 4`). Возвращаются бакеты, пересекающиеся с окном `[now-60s, now]`, и в списке **может быть несколько записей одного пакета** (например, на границе года или в зависимости от OEM). Цикл пишет `lastForegroundTime[pkg]` для каждой записи по очереди, и дельты между разными бакетами получаются мусорными (0 или ложные скачки).

**Последствие.** Потенциально — пропуски или завышение времени. Проявляется ли это на реальных устройствах, неизвестно: нужна проверка.

**Варианты решения:**
- ⭐ **Шаг 1 — диагностика (без изменения логики).** В `pollUsageStats` писать в `TrackingLogStorage` только при изменении: `size`, число уникальных пакетов и `firstTimeStamp/lastTimeStamp` бакетов. Прогнать на 2–3 устройствах. Если дублей нет, дальнейшие шаги не срочные.
- ⭐ **Шаг 2 — агрегация по пакету.** Заменить на `usageStatsManager.queryAndAggregateUsageStats(start, end): Map<String, UsageStats>`: одна запись на пакет, дубли исключены. Существующая логика «время пошло назад → сброс» остаётся на случай смены бакета.
- **Альтернатива — переход на события** `queryEvents()` (`ACTIVITY_RESUMED/PAUSED`, `MOVE_TO_FOREGROUND/BACKGROUND`): точный расчёт интервалов, в том числе реальных `startTime` сессий (сейчас `startTime = endTime - delta`). Самый точный, но и самый дорогой вариант (1.5–2 д + тесты). Имеет смысл, если сверка с «Цифровым благополучием» покажет заметные расхождения.

**Проверка:** сутки работы, итог за день сравнить с системной статистикой («Цифровое благополучие» / Digital Wellbeing).

### B-8. Гонка записи сессий и проверки лимитов

> **Решение (2026-09-23): ⏸ Отложено.** Игнорируем на данном этапе.

**Где:** `TrackingJob.kt:183-217`

**Проблема.** На каждый пакет с `delta > 0` запускается отдельный `GlobalScope.launch { trackUsageSession }`, и тут же параллельно `checkAlerts()` (тоже `GlobalScope.launch`). Проверка лимита может прочитать БД до того, как записана текущая минута.

**Последствие.** Алерт о превышении запаздывает до 1 минуты. Параллельные вставки для одного и того же нового пакета теоретически могут дважды выполнить `insertTrackedApp`.

**Варианты решения:**
- ⭐ **А.** В `pollUsageStats` сначала собрать список дельт синхронно, затем **одна** корутина: `GlobalScope.launch { deltas.forEach { trackUsageSession(it) }; alertManager.checkAndShowAlerts() }`. `GlobalScope` сохраняется (как зафиксировано в `CLAUDE.md`), меняется только порядок.
- **Б.** То же, но вставлять сессии одним `insertSessions(list)` в `@Transaction`-методе репозитория. Меньше обращений к БД, но надо сохранить проверку `isExcluded` и upsert `tracked_apps` для каждого пакета.

### B-9. Почасовые графики всегда считаются для «сегодня»

### B-10. Email-отчёт теряется, если пропущена минута отправки

> **Решение (2026-09-23): ✅ В работу.** Вариант **А** — «пора, и сегодня ещё не отправлено». Открытые вопросы при реализации: число попыток для `FAILED` и отправка сразу при включении после времени отправки (по варианту А — да).

**Где:** `EmailReportSender.kt:40-78`

**Проблема.** Отправка идёт только при `currentHour == sendHour && currentMinute == sendMinute`. Если в эту минуту таймер не сработал (Doze, убитый процесс, перезагрузка, задержка `Timer`), отчёт за день не уходит. Дедуп держится на `@Volatile lastSentAtMs` в памяти, поэтому перезапуск процесса в ту же минуту может дать повторную отправку. Лог `report_send_log` для принятия решения не используется.

**Варианты решения:**
- ⭐ **А. «Пора, и сегодня ещё не отправлено».**
  - Условие: `now >= сегодня HH:mm` **и** в `report_send_log` за сегодняшнюю дату нет записи со статусом `SUCCESS` или `PARTIAL`. Новый DAO-метод `hasSuccessfulReport(date): Boolean`; `getLogByDate` не подходит, так как записей за дату может быть несколько.
  - Дедуп на основе БД переживает перезапуск процесса. `lastSentAtMs` оставить как защиту от параллельного вызова в пределах процесса.
  - Политика для `FAILED`: не больше N попыток в день (например, 3, с интервалом ≥ 15 мин по `sentAt` последней записи). Иначе при отсутствии получателей или неверном пароле отправка будет повторяться каждую минуту и забивать лог.
  - Решить: если отчёт включили после времени отправки, уходит ли отчёт сегодня сразу? По варианту А — да.
- **Б. `AlarmManager.setExactAndAllowWhileIdle`** на время отправки + `WorkManager` для самой отправки с сетевым constraint. Надёжнее в Doze, но это новая инфраструктура, `SCHEDULE_EXACT_ALARM` на Android 12+ и повторное планирование после загрузки. Имеет смысл, только если вариант А на практике недостаточен.

**Проверка:** время отправки = текущее + 1 мин, в эту минуту убить процесс → после перезапуска сервиса отчёт уходит один раз. Повторный перезапуск второго письма не даёт.

### B-18. Побочные эффекты фильтра «< 1 мин» в `getDailyUsage`

> **Решение (2026-09-23): ✅ В работу.** Вариант **А** — фильтр «< 1 мин» только для отображения, итоги и лимиты — по всем сессиям.

### B-14. Слабый хэш пароля

> **Решение (2026-09-23): ⏸ Оставить как есть.** Вариант **В**. Текущий хэш сохраняется.

**Где:** `PrivateSettingsViewModel.kt:57, 74`, `UserRepository.kt:113`

**Проблема.** Пароль хранится как `password.hashCode().toString()`: 32-битный хэш без соли, подбирается перебором за доли секунды. Хэш лежит в DataStore `settings`. Попытки ввода никак не ограничены.

**Варианты решения:**
- ⭐ **А. PBKDF2 с прозрачной миграцией.**
  - `PasswordHasher` на `SecretKeyFactory.getInstance("PBKDF2WithHmacSHA256")` (доступен с API 26), соль 16 байт из `SecureRandom`, ~100–200 тыс. итераций (подобрать, чтобы вычисление занимало ~200 мс на слабом устройстве, и считать на `Dispatchers.Default`).
  - Формат хранения: `pbkdf2$<iter>$<saltB64>$<hashB64>`.
  - Проверка: если сохранённое значение без префикса `pbkdf2$` — это старый формат; сравнить через `hashCode()` и при успехе **сразу пересохранить** в новом формате. Пользователь ничего не замечает.
  - `initDefaultUser()` пишет дефолт `12345` уже в новом формате.
  - Проверку пароля перенести из ViewModel в `UserRepository` (сейчас хэширование живёт в UI-слое).
- **Б. Дополнительно:** задержка после N неверных попыток (например, 5 попыток → 30 с).
- **В. Оставить.** Модель угроз — ребёнок без ПК. Защита в первую очередь от ручного подбора, и здесь важнее Б, чем А.

> **Решение (2026-09-23): ✅ В работу.** Вариант **А** — шифрование ключом Android Keystore, зависимость `security-crypto` удалить.
