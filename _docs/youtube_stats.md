## 1. Задача (как поставлена)

Только для приложения YouTube (`com.google.android.youtube`) собирать данные о просмотренных видео:

- название видео;
- длительность видео (если возможно);
- тип — Shorts (reels) или обычный ролик (если возможно).

Показывать на экране "Детали приложения", агрегированно **посуточно** (00:00–23:59): если один и тот
же ролик просмотрен дважды за день — в UI одна запись. Место вставки в UI — между блоками "Сегодня" и
"Использование по часам" (см. `_docs/photo_2026-09-18_09-04-52.jpg`).

**Область действия этого этапа (уточнено пользователем):**
- Блок показывается **только** на экране "Детали приложения" для пакета `com.google.android.youtube`.
  Никакие другие экраны (в частности `HomeScreen` с вкладками "Сегодня"/"Вчера"/"Неделя" и любые другие
  общие списки/сводки использования) эти данные на этом этапе не показывают и не учитывают.
- В блоке показывается **только "сегодня"**. Переключателя/истории за прошлые дни ("вчера" и т.д.) в
  UI на этом этапе нет — только текущие сутки, как на референс-скриншоте.

## 2. Главное техническое ограничение

Разведка по текущему коду (`core/tracking/TrackingJob.kt`, `core/permissions/*`) показала:

- Весь трекинг сейчас построен на `UsageStatsManager.queryUsageStats()` — это даёт **только**
  суммарное foreground-время по пакету раз в минуту. Ни названия видео, ни его метаданных этот API
  в принципе не отдаёт.
- `UsageEvents`/`UsageEventsQuery` в проекте не используются и тоже не помогли бы — они дают только
  системные события переключения окон, не содержимое экрана.
- `AccessibilityService` в проекте отсутствует полностью: нет класса, нет объявления в манифесте, нет
  разрешения `BIND_ACCESSIBILITY_SERVICE`, нет пункта в `PermissionHelper`/`PermissionMonitor`.
- Официального YouTube Data API для этой задачи не подходит: он требует OAuth-аккаунт владельца
  контента/пользователя и не даёт "что сейчас реально открыто на экране постороннего приложения" —
  а нам нужно именно это, без интеграции с аккаунтом ребёнка.

**Вывод: единственный реализуемый на устройстве без root способ — новый `AccessibilityService`,
который читает дерево accessibility-нод экрана YouTube (аналог того, как читают экран скринридеры) и
извлекает из него текстовые поля.** Это отдельный, самый крупный кусок работы в этой фиче — всё
остальное (БД, UI, репозиторий) укладывается в существующие паттерны проекта почти без сюрпризов.

Важно понимать компромиссы такого подхода **до** начала реализации:

- Работает только пока экран YouTube активен на переднем плане и не заблокирован/не в фоне.
- Завязано на текущие `resourceId`/структуру layout'а приложения YouTube — Google меняет их между
  версиями без предупреждения; после обновления YouTube на телефоне ребёнка парсинг может частично
  или полностью сломаться до правки эвристик под новую версию. Это не разовая фича "сделал и забыл",
  а фича с постоянными эксплуатационными издержками.
- Приложение будет запрашивать у пользователя специальное системное разрешение "Специальные
  возможности" (Accessibility) — с точки зрения Android это разрешение того же уровня чувствительности,
  что и у скринридеров: сервис технически видит текст на экране *любого* приложения, если не
  ограничить его вручную. План ниже жёстко ограничивает обработку только пакетом YouTube, но сам факт
  включения разрешения в системных настройках будет выглядеть предупреждающе ("это приложение может
  видеть содержимое экрана").

## 3. Честная оценка по каждому пункту требования

| Данные | Достижимость | Комментарий |
|---|---|---|
| Название видео | Высокая | Заголовок стабильно есть в UI watch-экрана как текстовая нода; для Shorts — заголовок/описание тоже есть, но короче и не всегда полный. |
| Длительность видео | Средняя | На обычном watch-экране есть прогресс-бар с текстом вида `1:23 / 12:45` — общую длительность можно распарсить. Для Shorts многие ролики не показывают полную длительность в явном виде (лента бесконечного скролла) — здесь возможен только факт "короткое видео", без точной длительности. |
| Тип: Shorts / обычное видео | Высокая | У Shorts принципиально другой экран/навигация (вертикальная лента, свой набор resourceId), уверенно отличим от обычного watch-экрана по структуре ноды/имени класса окна. |

> Поле "возрастные ограничения" по решению пользователя в план не входит (было оценено как низкая
> достижимость — YouTube обычно не показывает явный бейдж возрастного рейтинга в UI watch-экрана).

Рекомендация: оставшиеся два поля реализовать как "best effort" — писать то, что удалось распознать,
`null`, если не удалось извлечь длительность, и не пытаться гарантировать 100% заполненность.

## 4. Архитектура решения

### 4.1 Новый пакет `core/youtube`

По аналогии с `core/tracking` и `core/alerts`:

- **`YoutubeAccessibilityService`** (`AccessibilityService`, объявляется в `AndroidManifest.xml` с
  `android:permission="android.permission.BIND_ACCESSIBILITY_SERVICE"` + `accessibility_service_config.xml`
  в `res/xml`, ограниченный `android:packageNames="com.google.android.youtube"` и
  `android:accessibilityEventTypes="typeWindowStateChanged|typeWindowContentChanged"`). Именно
  фильтр `packageNames` в конфиге — основной механизм "работаем только с YouTube", а не проверка
  вручную в коде (хотя проверку `event.packageName` дополнительно стоит оставить как defense-in-depth).
- **`YoutubeNodeParser`** — чистый Kotlin-объект без Android-зависимостей в сигнатуре снаружи
  (принимает уже извлечённый снимок текстовых полей/resourceId, а не сам `AccessibilityNodeInfo`,
  чтобы логику можно было покрыть JVM unit-тестами по аналогии с `AppUsageHourCalculator`,
  `DowntimeCalculator`). Отвечает за:
  - определение типа экрана (обычное видео / Shorts / не watch-экран — тогда событие игнорируется);
  - извлечение заголовка;
  - извлечение и парсинг строки длительности (`"12:45"`/`"1:02:10"` → мс).
- **`YoutubeVideoSnapshot`** — простая data-модель результата парсинга одного снимка экрана.
- Сервис на каждое релевантное accessibility-событие (с debounce, например 500–800 мс, чтобы не
  дёргать парсинг на каждое дрожание layout'а) снимает дерево корневого окна, прогоняет через
  `YoutubeNodeParser`, и если получил заголовок — передаёт результат в репозиторий (аналогично тому,
  как `TrackingJob` дергает `usageStatsRepository.trackUsageSession(...)`).

### 4.2 Хранение: новая таблица Room

По аналогии с `usage_sessions`/`UsageSessionEntity`/`UsageSessionDao`:

- **`YoutubeVideoViewEntity`** (таблица `youtube_video_views`):

  | Колонка | Тип | Назначение |
  |---|---|---|
  | `id` | `Long`, PK autoGenerate | |
  | `packageName` | `String` | всегда `com.google.android.youtube`, храним явно для единообразия с остальными таблицами |
  | `title` | `String` | заголовок видео — по нему делаем дедупликацию за сутки |
  | `videoType` | `String` | `"VIDEO"` / `"SHORTS"` / `"UNKNOWN"` |
  | `durationMs` | `Long?` | длительность видео, `null` если не удалось распознать |
  | `date` | `String` | `yyyy-MM-dd`, тот же формат и тот же способ вычисления "сегодня" (`SimpleDateFormat` от текущей даты), что и в `UsageSessionEntity`, для согласованности с остальной агрегацией |
  | `firstSeenAt` | `Long` | timestamp первого распознавания за день |
  | `lastSeenAt` | `Long` | timestamp последнего распознавания за день (обновляется при повторном просмотре) |
  | `viewCount` | `Int` | сколько раз за день зафиксирован повторный показ этого заголовка (для отладки/возможного будущего UI, в MVP можно не выводить) |

  Поле `date` нужно даже без UI-истории — это ключ посуточной дедупликации (см. раздел 5), а не задел
  под будущий экран истории. Хранение по дням в БД полезно и само по себе: retention 7 суток (4.6)
  подразумевает, что хоть какой-то диапазон дат в таблице будет, даже если UI показывает только сегодня.

  Уникальность на уровне таблицы: `UNIQUE(date, title)` (индекс), запись через `INSERT ... ON CONFLICT
  UPDATE lastSeenAt/viewCount` (Room `@Upsert` или ручной DAO-метод) — это и есть механизм "дважды
  просмотрено = одна запись в UI".

  **Ограничение дедупликации:** ключ — точный текст заголовка за день. Если YouTube показывает чуть
  разные варианты заголовка (обрезка/лишний пробел/смена локали в разных местах интерфейса), возможны
  ложные дубли. Это стоит явно принять как компромисс MVP — стабильного `videoId` без официального API
  у нас нет.

- **Миграция**: судя по разведке, реальная версия схемы сейчас `4` (аннотация `@Database(version = 4)`,
  при этом константа `AppDatabase.DATABASE_VERSION = 3` не совпадает и нигде не используется — известная
  находка, см. `_docs/bd_tables.md`). Новую миграцию нужно делать `MIGRATION_4_5` (версия 4 → 5), а не
  ориентироваться на константу `DATABASE_VERSION`. Регистрация — как обычно: entity в
  `@Database(entities=[...])`, DAO-абстрактный метод в `AppDatabase`, миграция в `Migrations.kt`,
  `.addMigrations(..., MIGRATION_4_5)` и провайдер DAO в `di/AppModule.kt`.

- **`YoutubeVideoViewDao`**: `upsertView(...)`, `getViewsForDate(packageName, date): List<...>` (или
  `Flow`) — единственный метод чтения, нужный на этом этапе (только "сегодня"), — и
  `deleteOldViews(keepDate: String)` по аналогии с `UsageSessionDao.deleteOldSessions`, нужен сразу
  (не "возможно"), так как очистка входит в объём этой фичи, см. 4.6. Метод для чтения диапазона дат
  на этом этапе не нужен — если в будущем понадобится история/неделя, это отдельное расширение поверх
  уже существующей таблицы, а не часть текущего плана.

### 4.3 Domain / Repository

- Доменная модель `YoutubeVideoView(title, videoType, durationMs, viewCount, date)`.
- Новые методы в `UsageStatsRepositoryImpl` (по аналогии с `getTodaySessionsForPackage`, которая тоже не
  вынесена в общий интерфейс `UsageStatsRepository`):
  - `getTodayYoutubeVideos(date): List<YoutubeVideoView>` — единственный метод чтения на этом этапе, для
    блока "сегодня" на `AppDetailScreen`;
  - `recordYoutubeVideoView(snapshot: YoutubeVideoSnapshot)` — запись, вызывается из
    `YoutubeAccessibilityService`.

### 4.4 UI

- В `AppDetailViewModel.loadAppDetail()` — если `packageName == "com.google.android.youtube"`,
  дополнительно грузим `repository.getTodayYoutubeVideos(today)` в `AppDetailState` (новое поле,
  например `youtubeVideos: List<YoutubeVideoView> = emptyList()`).
- В `AppDetailScreen.kt`, в `AppDetailContent`, между Card "Сегодня" (после текущего блока
  "Время использования"/"N сессий") и вызовом `AppUsageHourlyChart(...)` — новый Composable-блок,
  рендерится только когда список не пуст (то есть фактически только для YouTube с распознанными
  данными за сегодня):
  - заголовок секции, например "Просмотренные видео сегодня";
  - список карточек/строк, на каждую — заголовок видео, бейдж типа (Shorts/Видео), длительность (если есть).
- Для всех остальных приложений (не YouTube) блок просто не рендерится — экран "Детали приложения"
  остаётся неизменным.
- Никакого переключателя "Сегодня"/"За неделю" в этом блоке нет и никакой другой экран (в частности
  `HomeScreen`) эти данные не показывает — см. уточнение области действия в разделе 1. Если в будущем
  понадобится история по дням, это отдельная фича поверх уже накопленных в таблице данных (см. 4.6 про
  то, что данные всё равно хранятся 7 суток, даже не будучи показанными).

### 4.5 Разрешения / онбординг

- Новый пункт в `PermissionHelper` (`isAccessibilityServiceEnabled()` — проверка через
  `Settings.Secure.ACCESSIBILITY_ENABLED` + `ENABLED_ACCESSIBILITY_SERVICES`, открытие через
  `Settings.ACTION_ACCESSIBILITY_SETTINGS`) и в `PermissionMonitor`/`PermissionRepository`, по образцу
  существующих 4 разрешений.
- Решено: Accessibility-разрешение включается в общий онбординг, пятым пунктом в
  `OnboardingPermissions` (`usageStats`, `overlay`, `notifications`, `batteryOptimization`,
  `+ accessibilityService`), рядом с остальными обязательными разрешениями, а не отдельным опциональным
  шагом только для YouTube-фичи. Практическое следствие: `allGranted` в `OnboardingPermissions` теперь
  требует и это разрешение — если пользователь не включит Accessibility на онбординге, это будет
  выглядеть как незавершённый онбординг, как и с остальными 4 разрешениями. Экран онбординга должен
  внятно объяснить, зачем нужен именно этот пункт (в отличие от overlay/usage-stats, его назначение не
  так очевидно из названия в системных настройках).

### 4.6 Очистка старых записей (retention 7 суток)

Пользователь подтвердил, что нужна очистка, и указал ориентироваться на уже реализованный механизм —
`core/maintenance/DataCleanupManager.kt` (проверено: класс уже есть в коде, а не только в архивном
плане `_docs/archive/job_garbage_collector.md`). Сейчас он чистит 4 таблицы (`usage_sessions`,
`service_heartbeats`, `alert_logs`, `report_send_log`) с `RETENTION_DAYS = 7`, вызывается 4-м таймером
(`cleanupTimer`, раз в 12 часов) из `TrackingJob`.

Для `youtube_video_views` это не отдельный новый механизм, а **добавление в существующий класс**:

- В `DataCleanupManager.purgeOldData()` — ещё один блок, симметричный уже существующим (`try/catch` +
  `TrackingLogStorage.add("Cleanup", ...)`), вызывающий `youtubeVideoViewDao.deleteOldViews(keepDate)`
  (тот же `keepDate: String`, что уже вычисляется для `usage_sessions.date` — формат и cutoff совпадают,
  отдельный расчёт даты не нужен).
- В конструктор `DataCleanupManager` добавляется параметр `youtubeVideoViewDao: YoutubeVideoViewDao`
  (Hilt соберёт автоматически, как остальные 4 DAO, если `YoutubeVideoViewDao` уже провайдится в
  `di/AppModule.kt`, что и так требуется по разделу 4.2).
- Ретеншн — тот же `RETENTION_DAYS = 7`, отдельную константу под YouTube-таблицу заводить не нужно
  (пользователь попросил "старше недели", как у остальных таблиц — специального более короткого/длинного
  срока для видео не оговорено).
- Периодичность запуска, cron/таймер — без изменений (тот же `cleanupTimer` в `TrackingJob`, 12 часов),
  новой инфраструктуры заводить не требуется.
- В UI эти данные за прошлые дни не показываются (см. область действия в разделе 1) — retention 7 суток
  здесь чисто гигиеническая мера (не дать таблице расти бесконечно), а не задел под будущий экран истории.

## 5. Дедупликация посуточно — как это будет работать end-to-end

1. Сервис видит новый watch-экран YouTube → парсит заголовок/тип/длительность.
2. Вызывает `recordYoutubeVideoView` → репозиторий вычисляет `date = dateFormat.format(Date())` (тот же
   принцип, что и везде в `UsageStatsRepositoryImpl`) и делает upsert по ключу `(date, title)`.
3. Если такой `(date, title)` уже есть за сегодня — обновляется только `lastSeenAt`/`viewCount`, новая
   строка не создаётся.
4. `AppDetailViewModel` запрашивает список по `date = сегодня` → в UI ровно одна строка на уникальный
   заголовок, что и требуется по ТЗ.
5. Наступление следующих суток — начинается новый набор строк с `date` нового дня; данные за вчера не
   пропадают сразу, а хранятся в БД до истечения 7-дневного retention (см. 4.6), но в UI на этом этапе
   нигде не показываются — блок на `AppDetailScreen` всегда выводит только текущие сутки.

## 6. Риски и ограничения (сводно)

- **Хрупкость к обновлениям YouTube.** Основной риск всего решения. Эвристики парсинга resourceId/layout
  потребуют ревизии при заметных обновлениях YouTube на устройстве ребёнка; без телеметрии/логов сложно
  узнать, что парсинг "молча" перестал работать. Стоит закладывать использование существующего
  `TrackingLogStorage` для диагностики (аналогично remark в `CLAUDE.md` про `TrackingLogStorage` как
  де-факто лог трекинг-пайплайна) — писать туда события "не удалось распознать watch-экран" с
  минимальной частотой, чтобы не заспамить лог.
- **Батарея/производительность.** `AccessibilityService` с `typeWindowContentChanged` может дёргаться
  часто на активном YouTube-скролле (особенно в ленте Shorts) — обязателен debounce и по возможности
  игнор событий, не относящихся к самому watch/shorts экрану (проверка resourceId корневого окна перед
  тяжёлым обходом дерева).
- **Приватность.** Технически сервис получает доступ к содержимому экрана. Даже при ограничении
  `packageNames` в конфиге, само системное разрешение выглядит широким для пользователя, дающего его
  на устройстве ребёнка (обычно это не проблема, так как согласие даёт родитель, но стоит явно
  задокументировать в `INSTALL_GUIDE.md` при реализации, зачем это разрешение нужно).
- **Дубли по неточному совпадению заголовка** — см. п.4.2.
- **Несогласованность `AppDatabase.DATABASE_VERSION`** — существующая независимая находка (см.
  `_docs/bd_tables.md`), никак не блокирует эту фичу, но при добавлении `MIGRATION_4_5` нужно ориентироваться
  на реальную версию аннотации (4→5), а не на захардкоженную константу.

## 7. Тестирование

- `YoutubeNodeParser` — чистая функция, тестируется JVM unit-тестами (`app/src/test`) на заранее
  подготовленных фикстурах "снимков" дерева (título/resourceId в виде простых data-классов, без
  реального `AccessibilityNodeInfo`, который недоступен в JVM-тестах — то же ограничение, что уже
  описано в `CLAUDE.md` про `VendorHelperTest`/`Build.BRAND`).
- DAO/миграция — по аналогии с существующими Room-тестами (если есть) или ручной проверкой upsert-логики.
- Сам `AccessibilityService` и реальный парсинг живого дерева YouTube — **только ручное тестирование на
  подключённом устройстве/эмуляторе** с реально установленным YouTube (`connectedDebugAndroidTest`
  здесь малоприменим, так как зависит от живого стороннего приложения и его версии).

## 8. Поэтапный план работ

1. **БД**: `YoutubeVideoViewEntity`, `YoutubeVideoViewDao` (`upsertView`, `getViewsForDate`,
   `deleteOldViews`), `MIGRATION_4_5`, регистрация в `AppDatabase`/`AppModule` — без UI, проверяется
   тестами/сборкой.
2. **Очистка**: добавить блок под `youtube_video_views` в уже существующий
   `DataCleanupManager.purgeOldData()` (4.6) — можно сделать сразу вместе с п.1, отдельного нового
   механизма не требуется.
3. **Разрешение**: `PermissionHelper`/`PermissionMonitor`/`PermissionRepository` — добавление проверки
   Accessibility-разрешения; встраивание пятым пунктом в `OnboardingPermissions` и в экран онбординга
   (4.5), без реального сервиса ещё.
4. **AccessibilityService + парсер**: `YoutubeAccessibilityService`, `YoutubeNodeParser`,
   `accessibility_service_config.xml`, запись в БД через репозиторий. Реализуется и отлаживается
   итеративно на реальном устройстве с YouTube — это самый долгий и неопределённый по времени этап
   из-за живой зависимости от чужого UI.
5. **Domain/Repository методы**: `getTodayYoutubeVideos`, `recordYoutubeVideoView`.
6. **UI**: новый блок в `AppDetailScreen`/`AppDetailViewModel` (4.4), видимый только для YouTube,
   показывает только сегодняшние данные, нигде больше в приложении не отображается.
7. **Документация**: обновить `INSTALL_GUIDE.md` — новое обязательное разрешение (Accessibility) и что
   оно даёт, плюс упомянуть, что данные о видео хранятся не дольше 7 суток (даже не будучи показанными
   в UI за прошлые дни).

## 9. Решения, зафиксированные пользователем

| Вопрос | Решение |
|---|---|
| Возрастные ограничения | Убраны из плана полностью, не реализуются |
| Место запроса Accessibility-разрешения | Общий онбординг, пятым обязательным пунктом |
| Область показа данных | Только блок на `AppDetailScreen` для YouTube; на других экранах (`HomeScreen` и т.п.) не показывается |
| Глубина данных в UI на этом этапе | Только "сегодня"; истории/переключателя "за неделю" в UI нет |
| Очистка старых записей | Нужна, retention 7 суток, через существующий `DataCleanupManager` (4.6) — хранение в БД дольше "сегодня" нужно только для гигиенической очистки по расписанию, не для показа истории |
