# Экран "Детали приложения" — часовая диаграмма v2: горизонтальные столбики

> Это план, код не менялся (по просьбе пользователя — только планирование). Составлен по результатам
> чтения текущего кода, ветка `master`, коммит `b979c87` (v1 уже реализован — см. `_docs/app_detail_shema.md`
> и чек-лист в конце того файла, все пункты выполнены). Все ссылки на файлы/строки актуальны на этот момент.

## 1. Задача

В v1 (`_docs/app_detail_shema.md`) блок "Сессии" заменили на столбчатую диаграмму `AppUsageHourlyChart`
(`AppDetailScreen.kt:201-290`) — 16 вертикальных столбиков (часы 06..21), подпись часа под столбиком
**через один** (`bucket.hour % 2 == 0`, строка 278).

**Проблема:** при подписи через один час неочевидно, какому именно столбику соответствует "непарный" час
(21:00, 19:00 и т.п.) — нужно считать через один или сопоставлять по глазомеру.

**Задача v2:** повернуть диаграмму на 90° — сделать столбики горизонтальными (растут слева-направо), а слева
разместить подпись часа для **каждой** строки в формате двух цифр с ведущим нулём ("06", "21") — тогда
каждая полоса однозначно привязана к своему часу, без пропусков подписей.

**P.S. из задачи:** график `ServiceDowntimeChart` (Debug-экран, простои сервиса) **не трогать** — остаётся
ровно в текущем виде (`ui/debug/DebugScreen.kt:472-576`), включая его текущую вертикальную/columns-раскладку.
Явно **не** выносить общий composable между `AppUsageHourlyChart` и `ServiceDowntimeChart` — после этой
правки у них разная геометрия (столбцы vs строки), общий код только усложнит оба места.

## 3. Текущая раскладка (v1) — для сравнения

`AppDetailScreen.kt:219-288`:
- Внешний `Row` (`horizontalArrangement = SpaceBetween`) — один `Column` **на час**, `Modifier.weight(1f)`.
- Внутри каждого `Column` — `Box` с `contentAlignment = BottomCenter`:
  - сетка — горизонтальные `Divider`, смещённые по Y (`offset(y = ...)`, шаг `chartHeight / gridLines`);
  - сам столбик — `Box.fillMaxHeight(bucket.usageMinutes / 60f)`, растёт от низа вверх;
  - под столбиком — `Text` с часом, **только если `hour % 2 == 0`** (иначе подписи столбиков налезали бы
    друг на друга по ширине).

## 4. Новая раскладка (v2) — строки вместо столбцов

Общая идея — транспонировать структуру: то, что было "one `Column` per hour" внутри `Row`, становится
"one `Row` per hour" внутри `Column`. Ось роста бара меняется с `fillMaxHeight(fraction)` на
`fillMaxWidth(fraction)`.

### 4.1 Структура одной строки (один час)

```
Row (одна на час, vertical align = CenterVertically) {
    Text("06")            // фиксированная ширина, подпись часа — ПОКАЗЫВАЕТСЯ ВСЕГДА
    Spacer(8.dp)
    Box (weight = 1f, fillMaxHeight) {   // дорожка бара
        // вертикальные линии сетки (фон)
        // сам горизонтальный бар (поверх)
    }
}
```

- **Подпись часа** — `Text(bucket.hour.toString().padStart(2, '0'), ...)` в столбце фиксированной ширины
  (например `Modifier.width(28.dp)`, `textAlign = TextAlign.End` или `Center`) — без условия `hour % 2 == 0`:
  в горизонтальной раскладке строки не мешают друг другу по высоте, поэтому подписывается **каждый** из 16
  часов. Это и есть решение исходной проблемы — не нужно считать "через один", час всегда рядом со своей
  полосой.
- **Дорожка бара** (`Box`, `Modifier.weight(1f).fillMaxHeight()`, `contentAlignment = Alignment.CenterStart`):
  - фон/сетка — по аналогии с v1 (`gridLines = 6`), но линии теперь **вертикальные** и делят дорожку по
    ширине, а не по высоте: `for (i in 1 until gridLines)` → `Box(Modifier.fillMaxWidth(i / gridLines.toFloat()), contentAlignment = Alignment.CenterEnd) { /* тонкая вертикальная линия */ }` — тот же приём, что в v1
    (`fillMaxWidth(fraction)` + выравнивание по краю), только ось X вместо Y; так фракция не зависит от
    того, что в v1 было "через фиксированный `chartHeight` в dp" — здесь ширина дорожки динамическая
    (зависит от экрана), поэтому именно вариант с `fillMaxWidth(fraction)` + `Alignment...End`, а не
    `offset(x = ...)` от фиксированного значения в dp (в отличие от v1, где `chartHeight` было константой
    и `offset(y=...)` в dp работал корректно).
  - вертикальная линия — тонкий `Box` (`Modifier.fillMaxHeight().width(0.5.dp).background(outlineVariant
    alpha 0.3f)`) либо `androidx.compose.material3.VerticalDivider` (в проекте уже `material3:1.3.1`,
    `VerticalDivider` там есть, сигнатура аналогична уже используемому `Divider`) — выбор реализации не
    принципиален, оставить на этапе реализации; вариант с ручным `Box` чуть более consistent с тем, что в
    проекте и так нет сторонних чарт-либ и упор на простые примитивы (см. `_docs/app_detail_shema.md §2.4`).
  - сам бар — `Box(Modifier.fillMaxHeight().fillMaxWidth(bucket.usageMinutes / 60f).background(primary,
    shapes.extraSmall))`, растёт от левого края дорожки вправо. Ровно та же формула доли
    (`usageMinutes / 60f`), что в v1, просто применяется к `fillMaxWidth`, а не `fillMaxHeight`.

### 4.2 Структура всего графика

```
Column (16 Row, одна на час) {
    verticalArrangement = Arrangement.spacedBy(2.dp)  // v1: horizontalArrangement = SpaceBetween
}
```

- Высота одной строки — фиксированная константа, например `rowHeight = 20.dp` (высота, при которой подпись
  часа и тонкий бар помещаются без обрезки — подобрать при реализации).
- Итоговая высота чарта: `16 * rowHeight + 15 * 2.dp` (интервалы) ≈ 16×20 + 30 ≈ **350dp** — заметно больше,
  чем фиксированная высота в v1 (`chartHeight + 32.dp` = **128dp**), потому что теперь 16 меток идёт по
  вертикали, а не размазано по горизонтали в один ряд.
- Фон дорожки/скругление внешнего контейнера (`surfaceContainerLow`, `shapes.small`) — переносится с
  внешнего `Row` (v1) на внешний `Column` без изменений в подходе.
- Текст-сводка над графиком (`"Использование по часам (06:00–22:00)"`, `AppDetailScreen.kt:212-217`) —
  не меняется.

## 5. Риск: экран без скролла

`AppDetailContent` (`AppDetailScreen.kt:108-114`) — внешний `Column` **не оборачивает контент в
`verticalScroll`**, у него просто `fillMaxSize().padding(...)`. В v1 это не было проблемой: чарт занимал
фиксированные ~128dp, вместе с карточкой заголовка приложения и карточкой "Сегодня" контент, судя по всему,
укладывался в экран.

С переходом на горизонтальную раскладку высота чарта вырастает примерно в 2.5–3 раза (≈128dp → ≈350dp).
На небольших экранах (или при увеличенном системном шрифте) итоговый контент рискует не влезть в высоту
экрана — а так как скролла нет, лишнее просто срежется по нижней границе `Scaffold`.

**Решение (согласовано):** в рамках этой задачи добавить `.verticalScroll(rememberScrollState())` на внешний
`Column` в `AppDetailContent` (`AppDetailScreen.kt:108-113`, рядом с `fillMaxSize()`) — иначе новый график
может обрезаться на части устройств. Это небольшое, но реальное побочное изменение, вытекающее именно из
смены ориентации графика, а не самостоятельная доработка — входит в объём этой задачи, а не отдельный тикет.
