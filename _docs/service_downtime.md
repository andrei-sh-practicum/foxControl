# Простои сервиса трекинга — вывод в UI

> План. Реализация — только по отдельному запросу.

## 0. Контекст и решение

Изначальный дизайн (`_docs/bd_tables.md`) предполагал таблицу `service_downtime_events`,
куда простои должны были писаться отдельным шагом, а UI — читать готовые записи. По факту
`UsageStatsRepositoryImpl.recordDowntime()` никем не вызывается — таблица всегда пуста, писать
в неё некому.

**Решение (зафиксировано с пользователем):** таблицу `service_downtime_events` не используем и
вырезаем. Простои вычисляются **на чтении**, по разрывам между соседними записями
`service_heartbeats` (пишутся каждые 60с из `TrackingJob`, пока жив `TrackingForegroundService`).
Это проще, не требует отдельного шага записи и не может рассинхронизироваться с реальностью.

Зафиксированные с пользователем решения по алгоритму/UX:
- Разрыв, попавший на границу часа, целиком приписывается **часу начала** простоя (без
  пропорционального дробления между часами).
- Диаграмма грузится **один раз при открытии экрана** (как остальные данные Home), без
  автообновления в реальном времени.

## 1. Что вырезаем

Мёртвый код, к удалению:
- `data/local/entity/ServiceDowntimeEventEntity.kt` — файл целиком.
- `data/local/dao/ServiceDowntimeEventDao.kt` — файл целиком.
- `AppDatabase.kt`: `ServiceDowntimeEventEntity::class` из списка entities, `abstract fun serviceDowntimeEventDao()`.
- `di/AppModule.kt`: `provideServiceDowntimeEventDao(...)`.
- `data/repository/UsageStatsRepository.kt` (Impl): поле `serviceDowntimeEventDao`, метод `recordDowntime(...)`.
- `_docs/bd_tables.md`: убрать строку таблицы из списка + раздел `### service_downtime_events`;
  обновить формулировку в разделе `service_heartbeats` (там сказано "используется в связке с
  service_downtime_events" — заменить на факт, что простои считаются on-the-fly).

### Обязательная миграция БД

Удаление таблицы — это изменение схемы. Per `CLAUDE.md`, нельзя полагаться на
`fallbackToDestructiveMigration()` — нужно:
1. Бампнуть `AppDatabase.DATABASE_VERSION` (3 → 4).
2. Добавить `MIGRATION_3_4` в `Migrations.kt`: `DROP TABLE IF EXISTS service_downtime_events`.
3. Зарегистрировать её в `di/AppModule.kt` (`.addMigrations(MIGRATION_2_3, MIGRATION_3_4)`).

`service_heartbeats` не трогаем — новый метод чтения (см. ниже) использует существующую колонку
`timestamp`, схема не меняется.

## 2. Алгоритм вычисления простоев

Константы:
- `HEARTBEAT_INTERVAL_MS = 60_000` (совпадает с интервалом таймера в `TrackingJob`).
- `DOWNTIME_THRESHOLD_MS = 90_000` (1.5×интервала — запас, чтобы не считать простоем обычный
  джиттер таймера).
- Окно отображения: `06:00`–`22:00` текущего календарного дня (локальное время устройства).

Шаги (выполняются в репозитории на чтении, без побочных эффектов):

1. Взять границы текущего дня (`dayStart` = 00:00:00.000 сегодня, `dayEnd` = 00:00:00.000 завтра).
2. Прочитать все `service_heartbeats` с `timestamp` в `[dayStart, dayEnd)`, по возрастанию.
3. Построить список разрывов между **соседними** записями: `gap_i = (hb[i-1].timestamp, hb[i].timestamp)`.
4. Добавить "открытый" разрыв `(последний heartbeat, now)`, если сервис не отбивался последние
   `DOWNTIME_THRESHOLD_MS` — иначе текущий, ещё длящийся простой не попадёт на диаграмму до
   следующего открытия экрана.
5. Отфильтровать разрывы короче `DOWNTIME_THRESHOLD_MS` — это не простой, а норма.
6. Каждый оставшийся разрыв обрезать по окну `06:00–22:00` (если разрыв целиком вне окна —
   выбросить; если частично — обрезать концы по границам окна).

   Обрезка нужна, иначе разрыв, начавшийся до 06:00 (например 05:50–06:15), будет по правилу
   "весь час начала" привязан к невидимому часу `05:00` и пропадёт с графика целиком, хотя 15
   минут из него попадают в видимое окно. После обрезки такой разрыв станет `06:00–06:15` и
   корректно уйдёт в столбец `06:00`.
7. Длительность обрезанного разрыва в минутах → в бакет часа **начала обрезанного разрыва**
   (то самое зафиксированное правило "целиком в час начала", но уже от обрезанных, а не сырых
   границ).
8. Если в один час попадает несколько отдельных разрывов — их минуты суммируются (максимум 60,
   так как разрывы не пересекаются и все лежат внутри одного 60-минутного часа).
9. Минуты → деления: `divisions = if (minutes <= 0) 0 else min(6, ceil(minutes / 10.0))`.
   Проверка по примерам из задачи: 5 мин → `ceil(0.5)=1` ✓; 33 мин → `ceil(3.3)=4` ✓; 60 мин → `6` ✓.

Результат — список из 16 элементов (часы `06`..`21`, т.е. 16 столбцов `06:00–07:00` …
`21:00–22:00`), даже если простоев не было (все нули).

Намеренно **не** вычитаем "нормальный" 60-секундный такт из длительности разрыва перед бакетингом
(т.е. считаем сырую длительность разрыва, а не `разрыв − интервал`) — при пороге в 90с погрешность
не переходит границы 10-минутных делений почти никогда, а лишнее вычитание усложняет алгоритм без
заметной пользы. Если на реальных данных окажется, что это создаёт заметные искажения — можно
добавить вычитание позже.

## 3. Слои и файлы

### 3.1 Чистая функция (без Android/Room) — тестируемая

Новый файл `core/tracking/DowntimeCalculator.kt`:

```kotlin
data class DowntimeHourBucket(
    val hour: Int,             // 6..21
    val downtimeMinutes: Int,
    val divisions: Int         // 0..6
)

object DowntimeCalculator {
    fun calculate(
        heartbeatTimestamps: List<Long>, // отсортированы по возрастанию, за текущий день
        now: Long,
        windowStartHour: Int = 6,
        windowEndHour: Int = 22
    ): List<DowntimeHourBucket>
}
```

Логика — шаги 3–9 из раздела 2. Чистая функция от списка `Long` — без Room, без `Context`,
легко покрыть JVM unit-тестом (`app/src/test`) по аналогии с `VendorHelperTest`: разрыв внутри
часа, разрыв на границе часа, разрыв до 06:00 частично внутри окна, разрыв полностью вне окна,
открытый разрыв "по сей день", несколько разрывов в одном часе, отсутствие данных.

### 3.2 DAO

`ServiceHeartbeatDao` — добавить один метод (без миграции, колонка уже есть):

```kotlin
@Query("SELECT * FROM service_heartbeats WHERE timestamp >= :dayStart AND timestamp < :dayEnd ORDER BY timestamp ASC")
suspend fun getHeartbeatsBetween(dayStart: Long, dayEnd: Long): List<ServiceHeartbeatEntity>
```

### 3.3 Репозиторий

Добавить в домен-интерфейс `domain/repository/UsageStatsRepository.kt` (не только в Impl) —
это read-only модель для UI-экрана, тот же характер, что `getDailyUsage`/`getTopApps`, а не
tracking/heartbeat-запись, которая по конвенции проекта живёт только в `UsageStatsRepositoryImpl`:

```kotlin
suspend fun getServiceDowntimeBuckets(date: String): List<DowntimeHourBucket>
```

Реализация в `UsageStatsRepositoryImpl`: посчитать `dayStart`/`dayEnd` из `date` (`yyyy-MM-dd`,
как и остальные методы репозитория), вызвать `serviceHeartbeatDao.getHeartbeatsBetween(...)`,
передать таймстампы + `System.currentTimeMillis()` в `DowntimeCalculator.calculate(...)`.

### 3.4 ViewModel (`ui/home/HomeViewModel.kt`)

- `HomeState` — добавить `val downtimeBuckets: List<DowntimeHourBucket> = emptyList()`.
- Загрузка данных **не завязана** на переключение периода — отдельный вызов `loadDowntimeChart()`
  из `init {}`, один раз, без пересчёта при переключении Today/Week (данные всё равно всегда за
  "сегодня"). Рендерится результат только внутри вкладки Today (см. 3.5) — во вкладке Week поле
  `downtimeBuckets` просто не используется.

### 3.5 UI (`ui/home/HomeScreen.kt`)

Новый композабл `ServiceDowntimeChart(buckets: List<DowntimeHourBucket>)` размещается **внутри
контента вкладки Today** (там, где сейчас рендерится `state.dailyStats`), а не над переключателем
Today/Week: данные о простое всегда за "сегодня", во вкладке Week им не место. Порядок внутри
вкладки Today — диаграмма простоя первой (сверху), затем сводка использования и список приложений
(как сейчас), т.е. переключатель периода остаётся выше всего и не трогается.

Реализация — обычными Compose-примитивами (`Row`/`Column`/`Box` с весами/`fillMaxHeight(fraction)`),
без стороннего chart-lib: в проекте сейчас нет зависимости для графиков, а 16 столбиков × 6
делений — тривиальная разметка, тащить библиотеку под это избыточно.

Структура:
- Заголовок/сводка сверху: `"Простои сегодня (06:00–22:00): N мин"` (сумма по всем бакетам), либо
  `"Простоев не было"`, если сумма 0 — чтобы не заставлять родителя расшифровывать пустой график.
- Сама диаграмма: `Row` из 16 столбцов. Каждый столбец — `Box` высотой `divisions/6` от общей
  высоты диаграммы (например 96.dp), с `HorizontalDivider`-подобными линиями-делениями фона (6
  горизонтальных гридлайнов) для читаемости уровня.
- Подписи часов под столбцами: все 16 подписей мелким шрифтом не влезут по ширине комфортно на
  400px-экране — предлагаю подписывать через одну (`06, 08, 10, ... 22`), это стандартная практика
  для узких баров.
- Цвет столбика — нейтральный акцент темы; при `divisions >= 4` (простой ≥30 мин в час) можно
  подсвечивать предупреждающим цветом (`error`/`tertiary` в зависимости от темы) — по желанию,
  не критично для первой версии.
- Доступность: у каждого столбца `contentDescription`/`semantics` вида `"14:00–15:00: простой 33 минуты"`.

## 5. Открытые допущения (не переспрашивал, но стоит проверить при реализации)

- Окно `06:00–22:00` и день — **только "сегодня"**, без навигации по датам (это виджет-статус на
  Home, а не отдельный отчётный экран). Если понадобится история простоев за прошлые дни — это
  отдельная фича (например, на экране Debug, где уже есть похожий паттерн вкладок).
- Простой **до самого первого** heartbeat дня не считается (нет опорной точки "когда сервис должен
  был начать") — график покажет 0 в ранние часы, даже если сервис реально стартовал только в 08:00.
- Если за сегодня вообще нет heartbeat-записей (например, свежая установка) — все 16 бакетов 0,
  график пустой, без ошибки.
