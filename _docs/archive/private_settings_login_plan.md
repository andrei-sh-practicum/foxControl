# Приватные настройки: экран входа по паролю — план реализации

## 1. Как это работает сейчас (по коду)

Файлы: `ui/settings/PrivateSettingsScreen.kt`, `ui/settings/PrivateSettingsViewModel.kt`,
`data/repository/UserRepository.kt` (DataStore-часть).

Гейт (`PrivateSettingsGate` в `PrivateSettingsScreen.kt`) сегодня работает как экран **создания или ввода**
пароля в зависимости от `state.hasPassword`:

- `hasPassword == false` → режим `isSetMode = true`: заголовок "Создайте пароль", кнопка
  **"Установить пароль"** (`OnSetPassword` → `viewModel.setPassword()` → сразу `isAuthenticated = true`).
- `hasPassword == true` → режим `isSetMode = false`: заголовок "Введите пароль", кнопка **"Войти"**
  (`OnPasswordEntered` → `viewModel.verifyPassword()`), плюс кнопка **"У меня есть пароль"**, позволяющая
  вручную переключиться обратно в режим создания пароля даже когда пароль уже задан.

При этом обнаружены два бага, из-за которых вход по паролю сегодня фактически не работает так, как задумано:

1. **`PrivateSettingsState.passwordHash` никогда не заполняется.** В `init()` `ViewModel` подписывается на
   `userRepository.passwordHash` и обновляет только `hasPassword`/`isLoading`, но не кладёт сам хэш в
   `state.passwordHash`. А `verifyPassword()` сравнивает введённый пароль именно с `state.value.passwordHash`,
   которое всегда `null`. Результат: как только пароль установлен (`hasPassword = true`) и экран открыт заново,
   **любой ввод пароля даёт "Неверный пароль"**, даже правильный. Работает только "мгновенный" вход сразу
   после `OnSetPassword` (там `isAuthenticated = true` выставляется напрямую, минуя `verifyPassword`).
2. **Дефолтный пароль `"12345"` из `INSTALL_GUIDE.md` в реальности нигде не проставляется.**
   `UserRepository.initDefaultUser()` — единственное место, где `passwordHash` инициализируется значением
   `"12345".hashCode()`, — **не вызывается ни из одного экрана** (проверено по всему `app/src/main`:
   `ensureDefaultUser()` вызывается из `OnboardingViewModel`/`SettingsViewModel`, а `initDefaultUser()` — нет).
   Поэтому на чистой установке `passwordHash` в DataStore остаётся `null`, `hasPassword = false`, и гейт
   сегодня показывает не "Введите пароль", а режим создания пароля с нуля — документация с "12345" не
   соответствует поведению.

Прочее по гейту:
- `PrivateSettingsEvent.OnSetPassword` используется только в этом гейте (для сценария "первого запуска").
- `error` в `state` используется для текста под полем ввода; `OnClearError` объявлен, но нигде не вызывается
  (не в скоупе задачи).

## 2. Целевое поведение (по ТЗ)

Гейт всегда выглядит как экран входа, без ветвления "создать/ввести":

- Информация: **"Введите пароль"**.
- Поле ввода: **Пароль**.
- Кнопка: **"Вход"**.
- **"Назад"**.

По нажатию "Вход": сверяем введённый пароль с `UserRepository.passwordHash` (DataStore), у которого дефолт —
`"12345"`.
- Совпало → пропускаем внутрь раздела "Приватные настройки" (`isAuthenticated = true`).
- Не совпало → показываем ошибку, остаёмся на гейте.

Экрана "создания пароля" при первом входе больше нет — пароль всегда считается заданным (по умолчанию —
`"12345"`), сменить его можно только изнутри раздела через существующую кнопку **"Сменить пароль"**
(`ChangePasswordDialog`, не меняется).

## 3. Что нужно исправить, чтобы это заработало

Раз дефолтный пароль "12345" должен реально работать, а не просто быть написан в `INSTALL_GUIDE.md`, нужно
почитать оба найденных бага:

1. **Досеять дефолтный пароль.** Вызвать `userRepository.initDefaultUser()` в `OnboardingViewModel.initApp()`
   рядом с уже существующим `userRepository.ensureDefaultUser()` — этот метод и так гарантированно выполняется
   на каждом холодном старте приложения (Onboarding — стартовый экран), т.е. к моменту, когда пользователь
   вообще может дойти до "Приватных настроек", хэш пароля в DataStore уже будет проставлен (либо дефолтный
   `"12345"`, либо ранее заданный пользователем — `initDefaultUser()` не перезаписывает непустой хэш).
2. **Починить `PrivateSettingsViewModel.init()`** — при подписке на `userRepository.passwordHash` класть
   значение не только в `hasPassword`, но и в `state.passwordHash`, чтобы `verifyPassword()` реально сверял
   пароль, а не всегда возвращал `false`.

Без этих двух правок переход на "всегда режим входа" сломает вход полностью (пароль либо не с чем сравнивать,
либо сравнение всегда ложно).

## 4. Изменения в UI (`PrivateSettingsScreen.kt`)

`PrivateSettingsGate`:
- Убрать параметр `hasPassword` и локальное состояние `isSetMode`.
- Убрать ветвление текста — всегда "Введите пароль" / "Введите пароль для доступа к приватным настройкам".
- Убрать кнопку "Установить пароль" и логику `onSetPassword`.
- Убрать кнопку "У меня есть пароль" (переключение режимов больше не нужно).
- Единственная кнопка действия — **"Вход"**, вызывает `onPasswordEntered(password)` (это уже
  `PrivateSettingsEvent.OnPasswordEntered`, логика не меняется).
- Кнопка "Назад" — без изменений.

`PrivateSettingsScreen` (композable верхнего уровня): убрать проброс `hasPassword`/`onSetPassword` в
`PrivateSettingsGate`.

## 5. Изменения в `PrivateSettingsViewModel.kt`

- В `init()` — добавить `passwordHash = hash` в `_state.update { it.copy(...) }` при сборе
  `userRepository.passwordHash`.
- `PrivateSettingsEvent.OnSetPassword` и `PrivateSettingsViewModel` ветка `is OnSetPassword ->` становятся
  неиспользуемыми после удаления UI-сценария создания пароля — предлагается удалить их как мёртвый код
  (сам приватный `setPassword()`/`changePassword()` остаётся — их использует `ChangePasswordDialog`).
- `PrivateSettingsState.hasPassword` — после удаления `isSetMode`-ветки в UI становится неиспользуемым полем
  в проде; используется только в `PrivateSettingsStateTest`. Предлагается удалить поле и обновить тест
  (или оставить поле как есть, если хочется меньше диффа — вынесено в таблицу решений ниже).

## 6. `OnboardingViewModel.kt`

- В `initApp()` добавить вызов `userRepository.initDefaultUser()` сразу после
  `userRepository.ensureDefaultUser()`.

## 7. Пошаговый план реализации

1. `OnboardingViewModel.kt`: добавить вызов `userRepository.initDefaultUser()` в `initApp()`.
2. `PrivateSettingsViewModel.kt`: в `init()` заполнять `state.passwordHash` из потока; удалить
   `OnSetPassword` (event + обработка), при выбранном варианте — удалить `hasPassword` из `State`.
3. `PrivateSettingsScreen.kt`: упростить `PrivateSettingsGate` до единственного режима "вход" (см. п. 4).
4. `PrivateSettingsStateTest.kt`: обновить тесты, ссылающиеся на `hasPassword`, если поле удаляется.
5. Ручная проверка:
   - Чистая установка → онбординг → "Настройки → Приватные настройки" → пароль `12345` → вход успешен.
   - Неверный пароль → показывается ошибка "Неверный пароль", остаёмся на гейте.
   - "Сменить пароль" внутри раздела → выйти из раздела (кнопка "Назад") → зайти заново с новым паролем →
     вход успешен; со старым — ошибка.
   - Перезапуск приложения после смены пароля → пароль не откатывается на "12345" (т.к.
     `initDefaultUser()` не трогает непустой хэш).

## 8. Явные решения по умолчанию (можно поправить перед реализацией)

| Вопрос | Принятое решение |
|---|---|
| Где досеивать дефолтный пароль "12345" | `OnboardingViewModel.initApp()`, рядом с `ensureDefaultUser()` |
| Поле `PrivateSettingsState.hasPassword` | Удалить вместе с `isSetMode`-веткой как мёртвый код (плюс обновить тест) |
| `PrivateSettingsEvent.OnSetPassword` | Удалить как мёртвый код после упрощения гейта |
| Хэширование пароля (`String.hashCode()`) | Не трогаем — вне рамок этой задачи, меняется только экран входа |
| Текст ошибки при неверном пароле | Оставить как есть — "Неверный пароль" |
| Поведение кнопки "Назад" на гейте | Без изменений — выход из раздела на предыдущий экран |

## 9. Вне рамок этой задачи

- Стойкость хэширования пароля (`String.hashCode()` вместо криптографического хэша).
- Логика "Сменить пароль" внутри раздела (`ChangePasswordDialog`) — не меняется.
- Объединение DataStore-пароля с полем `users.passwordHash` в Room - не делаем.
