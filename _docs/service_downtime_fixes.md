# Простои сервиса — диаграмма по минутам (новая версия плана)

Полностью заменяет предыдущую версию этого
> файла (концепт «10-минутные деления / 0–6 divisions» выброшен целиком) и дополняет
> `_docs/service_downtime.md` в части алгоритма (раздел 2) и рендера (раздел 3.5) — там эти
> разделы теперь считаются устаревшими, актуальная версия — здесь.

## 0. Новый концепт (зафиксировано с пользователем)

- Столбик = 1 час. Общая высота столбика **всегда фиксирована и соответствует 60 минутам** —
  делений/уровней больше нет, шкала одна и та же для любого часа.
- Для каждого часа считаем:
  - `aliveMinutes` — сколько минут из этого часа сервис «жил» (есть heartbeat-покрытие);
  - `deadMinutes = 60 − aliveMinutes` — простой.
- Заливка столбика снизу вверх: сначала красным — `deadMinutes`, затем поверх — зелёным
  `aliveMinutes`, до верхней границы (60).
- **Часы/минуты без данных** (ещё не наступившие сегодня часы, и минуты ДО самого первого
  heartbeat за день, когда неизвестно, жил сервис или нет) — **не закрашиваются вообще** (ни
  красным, ни зелёным), т.е. остаются пустыми/фоновыми. Зафиксировано отдельно с пользователем:
  буквальное применение формулы `живые=0 → час целиком красный` для таких случаев даёт неверную
  картину (будущие часы выглядели бы как «полный простой», хотя они просто ещё не наступили).

## 1. Модель данных

Заменяет `DowntimeHourBucket` из `core/tracking/DowntimeCalculator.kt`:

```kotlin
data class DowntimeHourBucket(
    val hour: Int,           // 6..21
    val aliveMinutes: Int,   // 0..60
    val deadMinutes: Int     // 0..60
)
// Инвариант: aliveMinutes + deadMinutes <= 60.
// Остаток (60 − aliveMinutes − deadMinutes) — «нет данных» (будущее время суток или период
// до первого heartbeat дня) и на столбике не закрашивается никак.
```

Поля `divisions`/`MAX_DIVISIONS`/`MINUTES_PER_DIVISION` — убрать полностью, они были частью
старого «10-минутного» концепта.

## 2. Как считаем «живые» и «мёртвые» минуты — важное отклонение от буквальной формулировки

Буквально по задаче: «живые минуты = сколько минут из `service_heartbeats` сервис жил», что можно
прочитать как «посчитать, сколько отдельных календарных минут внутри часа содержат хотя бы один
heartbeat». **Предлагаю считать не так**, а через уже существующий в коде механизм гэпов
(`DOWNTIME_THRESHOLD_MS = 90_000`, т.е. 1.5× от интервала heartbeat в 60с):

- Собираем «мёртвые» интервалы как раньше — разрывы между соседними heartbeat ≥ 90с (плюс
  «открытый» разрыв от последнего heartbeat до `now`, если сервис прямо сейчас не отвечает
  дольше порога).
- `deadMinutes` часа = суммарное пересечение этих интервалов с окном часа (см. алгоритм ниже).
- `aliveMinutes` часа = «известное» время часа минус `deadMinutes` (а не отдельный прямой подсчёт
  «минут с heartbeat»).

**Почему не в лоб:** heartbeat пишется раз в 60с из `java.util.Timer`, но реальные метки всегда
немного «плавают» (доли секунды туда-сюда, паузы диспетчера ОС и т.п.). Если считать буквально
«календарная минута засчитана как живая только если в неё попал хотя бы один heartbeat», то
обычный дрейф вроде heartbeat в `10:14:58` и следующего в `10:16:03` (разрыв всего 65с — никакой
не простой) оставит минуту `10:15` без единой метки и она ложно покрасится красным. При текущей
частоте heartbeat такое дрожание — обычное дело, и на диаграмме это будет выглядеть как
хаотично разбросанные одиночные красные минуты каждый час, даже когда сервис работал стабильно.
Порог в 90с уже есть в коде именно для отсечения такого дрожания — логично посчитать через него, а
не вводить новый источник ложных срабатываний. Визуальный результат (красный снизу + зелёный
сверху, шкала 0–60) при этом получается ровно такой, как просили — меняется только то, **как**
внутри вычисляется `deadMinutes`, а не то, что видно на экране.

Если пользователь всё же хочет буквальный подсчёт «минута = есть ли heartbeat» — это отдельный
флаг на обсуждение, менять алгоритм на лету не буду без подтверждения.

## 3. Алгоритм (`DowntimeCalculator.calculate`)

Константы (без изменений): `HEARTBEAT_INTERVAL_MS = 60_000`, `DOWNTIME_THRESHOLD_MS = 90_000`,
окно `06:00–22:00`.

```
sorted = heartbeatTimestamps.sorted()
firstHb = sorted.firstOrNull()

// Мёртвые интервалы за весь день (как раньше) — считаем один раз
rawGaps = соседние пары sorted[i-1] to sorted[i]
if sorted не пуст && now - sorted.last() >= DOWNTIME_THRESHOLD_MS:
    rawGaps += (sorted.last() to now)          // «открытый» простой по сей момент
deadIntervals = rawGaps.filter { end - start >= DOWNTIME_THRESHOLD_MS }
    .clip(windowStartMs, min(windowEndMs, now))  // обрезаем по видимому окну и по "сейчас"
    .filterNot { пусто после обрезки }

for h in 6..21:
    hourStartMs, hourEndMs = границы часа h
    elapsedEndMs = min(hourEndMs, now)
    if elapsedEndMs <= hourStartMs:
        bucket(h, alive=0, dead=0)              // час ещё не наступил — пусто
        continue

    // Ничего не знаем про время до первого heartbeat дня — не считаем его ни живым, ни мёртвым
    knownStartMs = if (firstHb == null) elapsedEndMs else max(hourStartMs, firstHb)
    if knownStartMs >= elapsedEndMs:
        bucket(h, alive=0, dead=0)              // весь остаток часа — до первого heartbeat
        continue

    knownMinutes = (elapsedEndMs - knownStartMs) / 60_000
    deadMs = сумма пересечений deadIntervals с [knownStartMs, elapsedEndMs)
    deadMinutes = min(knownMinutes, deadMs / 60_000)   // считаем по суммарным мс, округляем один раз
    aliveMinutes = knownMinutes - deadMinutes
    bucket(h, aliveMinutes, deadMinutes)
```

Ключевое отличие от прошлой версии алгоритма: пересечение с окном часа считается **отдельно для
каждого часа** (`[knownStartMs, elapsedEndMs)` каждого бакета), а не «весь разрыв целиком в час
начала». Это заодно автоматически чинит найденный ранее баг «многочасовой простой целиком
приписывается одному часу и обрезается до 60 мин, остальное теряется» — теперь длинный простой
корректно размазывается по всем часам, которые он реально перекрывает.

Округление: суммировать миллисекунды пересечений и делить на 60 000 один раз в конце (а не
складывать уже округлённые минуты по отдельным сегментам), чтобы не накапливать ошибку округения
при нескольких разрывах в одном часе.

## 4. Рендеринг (`HomeScreen.kt`, `ServiceDowntimeChart`)

Из предыдущей версии этого документа остаётся в силе главный вывод: **не использовать
`Modifier.weight()`** для высоты закрашенной части — он делит место пропорционально между
присутствующими весовыми детьми и раздувает столбик на 100% высоты контейнера независимо от
фактической доли (это и был корень обеих старых проблем — несоответствия сумме и «роста вниз»).
С новой моделью (2 сегмента вместо переменного числа делений) грабля та же: если по ошибке снова
взять `weight(aliveMinutes/60f)` + `weight(deadMinutes/60f)`, Compose нормирует их между собой и
всё равно заполнит 100% контейнера даже для наступившего наполовину часа.

Правильный вариант — фиксированная высота через `fillMaxHeight(fraction)` (доля берётся от
constraints родителя, а не от соседей):

```kotlin
val chartHeight = 96.dp

Box(
    modifier = Modifier
        .fillMaxWidth()
        .height(chartHeight)
        .background(MaterialTheme.colorScheme.surfaceContainerLow, MaterialTheme.shapes.small),
    contentAlignment = Alignment.BottomCenter
) {
    // сетка-подложка (6 горизонтальных линий, по аналогии со старым кодом) — оставить как есть

    Column {
        if (bucket.aliveMinutes > 0) {
            Box(
                Modifier
                    .fillMaxWidth()
                    .fillMaxHeight(bucket.aliveMinutes / 60f)
                    .background(MaterialTheme.colorScheme.primary, MaterialTheme.shapes.extraSmall)
            )
        }
        if (bucket.deadMinutes > 0) {
            Box(
                Modifier
                    .fillMaxWidth()
                    .fillMaxHeight(bucket.deadMinutes / 60f)
                    .background(MaterialTheme.colorScheme.error, MaterialTheme.shapes.extraSmall)
            )
        }
    }
}
```

Порядок детей в `Column` важен: `aliveMinutes`-бокс объявлен первым (окажется сверху), `deadMinutes`
— вторым (окажется снизу) — соответствует «красным снизу, зелёным остаток до верха». Суммарная
высота `Column` = `chartHeight * (alive+dead)/60`; для полностью прожитого часа это `chartHeight`
(столбик занимает всё), для ещё идущего часа — меньше, и благодаря `contentAlignment =
Alignment.BottomCenter` внешнего `Box` недостающая часть автоматически остаётся пустой **сверху**
— именно то поведение, которое нужно для «ещё не наступивших» минут, без отдельного кода под этот
случай.

Цвета: `primary`/`error` как ориентир (как в старом коде для «критичных» делений) — конкретные
токены можно оставить как есть в реализации, не принципиально для плана.

Итоговая сумма в шапке не меняется по смыслу, только по источнику поля:

```kotlin
val totalDeadMinutes = buckets.sumOf { it.deadMinutes }
"Простои сегодня (06:00–22:00): $totalDeadMinutes мин"
```

## 7. Тест-кейсы для `DowntimeCalculatorTest`

- Нет heartbeat вообще за день → все 16 бакетов `(0, 0)`.
- Час полностью в прошлом, без разрывов → `(60, 0)`.
- Час полностью в прошлом, полностью внутри одного длинного (многочасового) простоя →
  `(0, 60)` — проверяет фикс бага «весь простой в один бакет».
- Простой на 90 минут, захватывающий границу двух часов (например `09:40–11:10`) — минуты
  распределяются по трём часам (`09`, `10`, `11`) пропорционально пересечению, не всё в один.
- Разрыв короче порога (60с, обычное дрожание) — не должен давать `deadMinutes > 0`.
- Час, который сейчас идёт (`now` внутри часа) — `aliveMinutes + deadMinutes == now-часть в
  минутах`, остаток до 60 не заполнен ни тем, ни другим.
- Час позже текущего момента (будущее) → `(0, 0)`.
- Час раньше первого heartbeat дня (например первый heartbeat в `07:15`, бакет `06`) → `(0, 0)`,
  простой до первого heartbeat не засчитывается ни в plus, ни в минус.
- Несколько отдельных разрывов внутри одного часа — суммируются в `deadMinutes` этого часа.

## 8. Зафиксированные и открытые допущения

Зафиксировано с пользователем в этом раунде:
- Часы вне «известного» диапазона (будущее сегодня, и период до первого heartbeat дня) —
  не закрашиваются ни красным, ни зелёным, просто пустые.

Осталось как допущение (перенесено из предыдущей версии документа, не переспрашивалось повторно):
- Порог простоя `90_000` мс и окно `06:00–22:00` — не трогаем, актуальны как есть.
- `deadMinutes` считается через существующий механизм гэпов (раздел 2), а не буквальным подсчётом
  «минут с heartbeat» — решение автора плана, стоит подтвердить при реализации, если важно именно
  буквальное поведение.
