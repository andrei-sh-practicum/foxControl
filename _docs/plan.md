# Fox Control — План реализации

> Приватное Android-приложение для родительского контроля времени использования смартфона.
> Основано на `draft.md`, дополнено решениями по открытым вопросам (см. раздел 1).

## 1. Зафиксированные решения (уточнено с заказчиком)

| Вопрос | Решение |
|---|---|
| Отправка email без бэкенда | Прямой SMTP с устройства (Jakarta Mail), credentials почты-отправителя хранятся в `EncryptedSharedPreferences` на устройстве |
| Min / Target SDK | `minSdk = 26` (Android 8.0), `targetSdk = 34/35` |
| Дистрибуция | Ручная установка APK (sideload), обновления — вручную (новый APK поверх старого, с сохранением данных) |

Эти решения фиксируют архитектуру фоновой работы, разрешений и доставки отчётов ниже.

## 2. Область действия (Scope)

**Входит в MVP:**
- Постоянный фоновый сбор статистики использования приложений (per-app, по дням/часам).
- Обнаружение простоев самого Fox Control (устройство выключено / приложение убито / permission отозван).
- Главный экран: статистика "сегодня" / "неделя" с переключателем.
- Суточный лимит на весь смартфон + суточный лимит на отдельное приложение.
- Оповещение (system overlay) при превышении лимита, поверх активного приложения.
- Ежедневная отправка отчёта на 1+ email в заданное время.
- Настройки: публичные (имя, аватар) и приватные (за паролем): лимиты, email-получатели, время отчёта, смена пароля.
- Онбординг с запросом всех системных разрешений.

**Не входит в MVP (см. `roadmap.md`, раздел "После MVP"):**
- Публикация в Google Play.
- Принудительная блокировка приложений (Device Owner / MDM режим) — есть только оповещение, не блокировка.
- Мульти-профиль (несколько детей на одном устройстве).
- Облачная синхронизация/бэкап статистики.
- Автоматическая категоризация "развлекательных" приложений через внешний каталог — используем эвристику + ручной whitelist.

## 3. Архитектура

### 3.1 Общая схема

Clean Architecture + MVVM, три слоя:

```
presentation/  Compose screens + ViewModels (StateFlow) + Navigation Compose
domain/        UseCases, доменные модели, интерфейсы репозиториев
data/          Room (DAO/Entity), UsageStatsManager-обёртка, SMTP-клиент,
               EncryptedSharedPreferences / DataStore, WorkManager Workers
```

DI — Hilt на всех слоях. Модуль приложения один (`app`), логическое разделение — по пакетам (`feature.home`, `feature.settings`, `feature.onboarding`, `core.tracking`, `core.email`, `core.data`).

### 3.2 Сбор статистики использования

- Источник данных — системный `UsageStatsManager` (`queryEvents` / `queryUsageStats`), требует разрешение `PACKAGE_USAGE_STATS` (`Settings.ACTION_USAGE_ACCESS_SETTINGS`, выдаётся вручную пользователем один раз).
- Фоновый `TrackingForegroundService` (foreground service, type `dataSync`/`specialUse` на Android 14+) периодически (напр. раз в 1 минуту) опрашивает `UsageEvents`, агрегирует активные сессии по `packageName` и пишет в Room.
- `WorkManager` periodic worker — резервный механизм на случай, если foreground service был убит системой (перезапуск + досбор пропущенных данных из `UsageStatsManager`, так как система сама хранит историю ~7 дней независимо от нашего сервиса).
- `BootReceiver` (`RECEIVE_BOOT_COMPLETED`) перезапускает сервис после перезагрузки устройства.
- Категория "развлекательные приложения" определяется комбинированно: `ApplicationInfo.category` (GAME, SOCIAL, VIDEO, ...) + ручной список исключений/дополнений, редактируемый в приватных настройках.

### 3.3 Обнаружение простоя Fox Control

Полностью надёжно на Android не гарантируется без root, поэтому — эвристика на основе нескольких сигналов:
- **Heartbeat-лог**: сервис пишет метку времени "жив" каждые N минут в Room. Разрыв между двумя метками > 2N трактуется как простой.
- **Boot time diff**: сравнение `System.currentTimeMillis() - SystemClock.elapsedRealtime()` между запусками — обнаруживает перезагрузку/выключение устройства.
- **Проверка отозванного разрешения**: при каждом опросе `UsageStatsManager` проверяется `AppOpsManager` статус `PACKAGE_USAGE_STATS` — если отозван, пишется событие "мониторинг остановлен пользователем" с таймстампом.
- Простои сохраняются как отдельные записи `ServiceDowntimeEvent(start, end, reason)` и отображаются в отчёте/UI как "нет данных за период X–Y".

### 3.4 Лимиты и оповещения

- `AppLimit(packageName, dailyLimitMinutes)` и `GlobalLimit(dailyLimitMinutes)` в Room, редактируются в приватных настройках.
- Проверка лимита выполняется в фоновом сервисе при каждом цикле опроса (см. 3.2).
- При превышении — `OverlayAlertService` рисует `TYPE_APPLICATION_OVERLAY` окно поверх текущего приложения (требует `SYSTEM_ALERT_WINDOW`, выдаётся вручную). Если overlay-разрешение не выдано — деградация до обычного heads-up уведомления.
- Дедупликация: одно оповещение на факт превышения лимита (не спамить каждую минуту), с возможностью повторного показа через настраиваемый интервал.

### 3.5 Email-отчёты

- Библиотека: `Jakarta Mail` (форк `javax.mail` для Android) поверх `INTERNET`-разрешения, прямое SMTP-соединение (TLS/587 или SSL/465).
- Конфигурация отправителя (SMTP host/port/login/app-password, from-address) — единая для приложения, хранится в `EncryptedSharedPreferences`. Задаётся один раз при первичной настройке (не описано в UI черновика — экран "Настройка почты-отправителя" добавляется в приватные настройки).
- Список получателей (`EmailRecipient(email, enabled)`) — в Room, управляется в приватных настройках.
- Отправка — точный однократный алярм в сутки (`AlarmManager.setExactAndAllowWhileIdle`, время из настроек, по умолчанию 20:00 Europe/Chisinau) → `SendReportWorker` формирует HTML/текстовый отчёт за истёкшие сутки и рассылает по списку получателей.
- Retry-политика при сетевой ошибке: до 3 попыток с backoff, лог результата (`ReportSendLog`) для диагностики в UI.
- Учитывать смену часового пояса/переход на летнее время при перепланировании алярма.

### 3.6 Данные по умолчанию и безопасность

- При первом запуске создаётся `User(name="username", passwordHash=hash("12345"), avatarUri=null)`.
- Пароль приватных настроек хранится хэшированным (не в открытом виде), напр. `BCrypt`/`Argon2` через небольшую зависимость или `MessageDigest` + соль как минимально достаточный вариант для privately-distributed приложения.
- Приватная секция открывается вводом пароля (без лимита попыток в MVP — не банковское приложение; можно добавить троттлинг позже).
- SMTP-пароль и пароль приватного раздела — единственные секреты приложения; оба в `EncryptedSharedPreferences` (Android Keystore-backed).

### 3.7 Модель данных (Room, основные таблицы)

| Таблица | Поля (кратко) |
|---|---|
| `User` | id, name, avatarUri, passwordHash, createdAt |
| `TrackedApp` | packageName, appName, iconUri, category, isEntertainment, isExcluded |
| `UsageSession` | id, packageName, startTime, endTime, durationMs, date |
| `AppLimit` | packageName, dailyLimitMinutes, enabled |
| `GlobalLimit` | dailyLimitMinutes, enabled |
| `EmailRecipient` | id, email, enabled |
| `ReportSettings` | sendTimeHHmm, lastSentDate, senderConfigured |
| `ReportSendLog` | id, date, status, error, sentAt |
| `ServiceHeartbeat` | timestamp |
| `ServiceDowntimeEvent` | id, startTime, endTime, reason |
| `AlertLog` | id, packageName, timestamp, type (global/app) |

### 3.8 Экраны (Navigation Compose)

1. **Onboarding** — пошаговый запрос разрешений (Usage Access → Overlay → Battery optimization exemption → Notifications) с объяснением, зачем каждое нужно; блокирует вход в приложение, пока критичные разрешения не выданы.
2. **Home (главный модуль)** — переключатель "Сегодня / Неделя", список приложений с временем использования, прогресс общего лимита.
3. **App Usage Detail** — детализация по конкретному приложению (график по часам/дням), точка входа к установке лимита.
4. **Settings — Public** — аватар, имя.
5. **Settings — Private Gate** — экран ввода пароля.
6. **Settings — Private** — общий лимит, топ-10 приложений за неделю + лимиты, email-получатели, время отправки отчёта, конфигурация SMTP-отправителя, смена пароля.
7. **Overlay Alert** — полноэкранное/оверлейное предупреждение о превышении лимита.

### 3.9 Версионирование сборок

- Разработка стартует с версии `0.1.0`; каждая сборка/компиляция APK обязана менять версию (нет двух APK с одинаковой версией).
- Схема — упрощённый SemVer (`MAJOR.MINOR.PATCH`), инкремент решает разработчик по типу изменений с предыдущей сборки:
  - Новая функциональность → минорная версия: `0.1.0 → 0.2.0`.
  - Исправление бага → патч-версия: `0.1.0 → 0.1.1`.
  - `MAJOR` в MVP не используется (зарезервирован под будущий релиз после `roadmap.md`, раздел "После MVP").
- `versionName`/`versionCode` в `build.gradle` — источник истины; `versionCode` инкрементируется на каждую сборку монотонно (требование Android), `versionName` — по правилам выше.
- Имя APK-файла обязано включать версию постфиксом: `app-debug_0.1.1.apk`, `app-release_0.2.0.apk` (настраивается через `android.applicationVariants.all { outputs... outputFileName }` в `build.gradle`).
- Текущая версия (`versionName`) выводится в UI на экране настроек (см. §3.8 — Settings, публичная или приватная секция, финальное место уточняется при реализации).
- После успешной компиляци файл apk должен быть скопирован в директорию `~/MEGA/APK` и на него должны быть выставлены права 777

### 3.10 Отладка и диагностика

**Обработка ошибок:**
- Потенциально проблемные фрагменты кода (I/O, сеть/SMTP, работа с `UsageStatsManager`, permissions, Room-транзакции и т.п.) оборачиваются в `try/catch`.
- Пойманные ошибки выводятся в UI (а не только в логи) — в месте, релевантном контексту (инлайн-сообщение на экране, диалог, запись в лог экрана типа `ReportSendLog`).
- Текст ошибки должен содержать контекст, достаточный для диагностики: что за операция, на каком шаге, исходное сообщение/код исключения — не просто "Произошла ошибка".

**System-сообщения (прозрачность процессов):**
- Опционально — по завершении одношагового процесса в UI показывается краткое подтверждающее сообщение (например, "Фотография успешно загружена").
- Обязательно — если процесс многоступенчатый, каждый шаг отражается отдельным сообщением, чтобы пользователь/разработчик видел, на каком этапе находится процесс и где он мог прерваться. Пример применительно к Fox Control (формирование и отправка суточного отчёта, см. §3.5):
  1. Данные использования за сутки собраны.
  2. Отчёт сформирован (HTML/текст).
  3. Отчёт отправлен получателю(ям).
  4. Результат отправки записан в `ReportSendLog`.
- Это правило применяется по мере реализации соответствующих многошаговых процессов (email-отчёты, онбординг с последовательным запросом разрешений и т.п.), а не только к примеру выше.

## 4. Технический стек

Стек из черновика подтверждён без изменений:

Kotlin 2.1.0 · AGP 8.7.3 · Jetpack Compose 1.7.8 · Material 3 1.3.1 · Navigation Compose 2.8.5 · Room 2.6.1 · Hilt 2.51.1 · Coroutines/Flow 1.7.3 · Coil 2.6.0 · EncryptedSharedPreferences 1.1.0-alpha06 · DataStore Preferences 1.1.1.

Дополнительно (не было в черновике, требуется под функционал):
- **Jakarta Mail (Android-friendly build)** — отправка SMTP-писем.
- **WorkManager** — фоновые/периодические задачи (агрегация, резерв опроса, ретраи отправки).
- Retrofit/Gson из черновика — в MVP не используются (нет сетевого API, кроме SMTP), оставлены про запас на случай будущей интеграции с внешним email API — решение отложено, зависимость не удаляется без запроса.

## 5. Разрешения (AndroidManifest)

`PACKAGE_USAGE_STATS` (via Settings intent) · `SYSTEM_ALERT_WINDOW` · `FOREGROUND_SERVICE` + `FOREGROUND_SERVICE_DATA_SYNC`/`SPECIAL_USE` · `RECEIVE_BOOT_COMPLETED` · `POST_NOTIFICATIONS` (API 33+) · `INTERNET` · `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`.

## 6. Риски и способы снижения

| Риск | Влияние | Митигация |
|---|---|---|
| OEM-агрессивное убийство фоновых процессов (Xiaomi/Samsung/Huawei) | Пропуски в статистике, невыполненные алярмы | Battery optimization exemption в онбординге + инструкция для конкретных вендоров; heartbeat для обнаружения и отображения пропусков честно, а не молчаливо |
| Пользователь (ребёнок) вручную отзывает Usage Access / Overlay permission | Потеря мониторинга | Периодическая проверка статуса разрешений, лог события в `ServiceDowntimeEvent`, отражение в отчёте на email |
| Gmail/провайдер блокирует прямой SMTP с обычным паролем | Отчёты не уходят | В плане закладывается использование App Password (2FA-аккаунт) как задокументированное требование к отправителю; статус доставки виден в приватных настройках (`ReportSendLog`) |
| Неточное определение "простоя" (нельзя всегда отличить выключение устройства от завершения приложения) | Ложные/пропущенные записи простоя | Комбинация нескольких сигналов (3.3), явная маркировка как "предположительно", а не факт |
| Изменение поведения `UsageStatsManager`/фоновых сервисов в будущих версиях Android | Регресс на новых OS | target API актуализируется по мере выхода новых версий, вынесено в бэклог "После MVP" |

## 7. Открытые вопросы для будущих итераций (не блокируют MVP)

- Конфигурация SMTP-отправителя: где именно в UI и как валидируется (тестовое письмо) — детализируется на этапе реализации email-модуля.
- Нужна ли история изменений лимитов (аудит "кто и когда менял")?
- Поведение при отсутствии интернета на момент отправки отчёта — только retry, или также локальное уведомление родителю на самом устройстве?
